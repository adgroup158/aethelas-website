How Aethelas Works

A complete walk-through of the Aethelas pipeline — from a signed transaction to a finalized block — including where the AI layer operates alongside the blockchain core, and where it does not.

Scope note: This model describes the current testnet implementation as of Q3 2026. It is a research-stage system, not a production network. All flows shown are implemented in the open-source codebase. Some components are marked planned where they are not yet fully wired.

02 · AI LAYER Where AI actually fits alongside, not inside, consensus

AI is not the consensus itself. It operates alongside the blockchain core as an advisory and security layer. Three subsystems read state and emit signals that the consensus and API layers can act on. Full details in TR‑04.

Hover a card — its layers separate in depth.

🧠

Validator Intelligence

Scores each validator's historical behaviour and computes a proposer weight. The score influences selection probability — it does not replace BFT.

  • uptime · participation
  • blocks_proposed · blocks_missed
  • votes_signed · double-sign detection
  • → proposer weight (0.5 – 3.0)
🔍

Transaction Intelligence

Classifies each incoming transaction with a risk score before mempool admission. This is the AIDecision record attached to every transaction.

  • spam detection (rate-window)
  • MEV pattern detection (gas distribution)
  • suspicious TX risk score
  • → approve / reject at mempool edge
🛡️

Threat Detection

Monitors the P2P layer for network-level attacks and writes a threat log that operators and the API can read.

  • Sybil (address-overlap detection)
  • Eclipse (peer-ID prefix diversity)
  • Sandwich (mempool pattern)
  • malicious peer flagging

03 · CRYPTOGRAPHY The cryptographic flow hash → sign → verify

A transaction is not "sent to a blockchain." It is hashed, signed, and then independently re‑verified by the node before it enters the mempool. Every step below is implemented in the current codebase.

Hover any card to lift it forward.

01

Wallet constructs the transaction

from · to · amount · nonce · gas · chain_id

02

SHA‑256 computes the transaction hash

hash = SHA-256(from:to:amount:nonce:gas:chain_id)

03

Ed25519 signs the hash

The private key produces a signature over the 32‑byte hash. chain_id binding prevents cross‑chain replay.

04

Node independently re‑computes and verifies

The node recomputes the hash, then verifies the signature against the sender's public key. It also checks nonce, balance, gas, and TX limits.

05

Accepted into mempool

If all checks pass, the transaction enters the mempool with a priority derived from gas price.

04 · CONSENSUS iPoS BFT consensus propose → prevote → precommit

Aethelas uses a Tendermint‑style BFT protocol with AI‑weighted proposer selection (iPoS). A block is finalized once two‑thirds of voting power reaches Precommit. Details in TR‑04.

Validators orbit the consensus core at three depths — the sweep arc marks quorum.

05 · BLOCK Block assembly layers → final block

A finalized block is not a monolith. It is an ordered stack of layers — previous hash, transactions, Merkle root, timestamp, validator signature, and finally the block hash itself. Watch them assemble and separate as the rotation cycles.

06 · STATE The state engine finalized block → persistent state

Once a block is finalized, the state engine executes each transaction and applies its effects. Every mutation is committed to RocksDB and becomes part of the permanent chain state.
